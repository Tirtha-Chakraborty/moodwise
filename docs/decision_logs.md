# Moodwise: Decisions Log

Decisions made on this project, and why. This log is append-only: a reversed decision gets a new row and the old row stays.

## Decisions

| Date | Decision | Rationale |

| 2026-10-03 | Backend-first, with one thin end-to-end slice per week (throwaway static page in Week 1, walking skeleton with `FakeClassifier` in Week 2, real LLM in Week 3). Rejected: stable frontend with dummy data first. | The UI is trivial in V1, the risk is in the backend, and the goal is backend learning. | 2026-11-01 | V1 is an end-to-end baseline: the LLM does one job (classify a phrase into a fixed mood or `unclear`) and everything after is a lookup in a hand-tagged dataset. Rejected: perfecting mood matching first. | Matching is replaced in V2, while the skeleton (handler, validation, deploy, tests) carries forward. You can't improve matching without a deployed loop and an eval to measure it. |
| 2026-11-01 | Bounded cost (spend guard) is an in-scope V1 requirement. The PRD states the requirement only; the mechanism is decided in the TDD (see Q5). Rejected: leaving it out until V4. | A public endpoint that spends money per request needs a safeguard. Matches Weekly Plan Week 4. |
| 2026-11-01 | V1 feedback is collected through a Google Form, linked on both the home page and the results page. Rejected: mailto link, storing feedback in the backend. | No database in V1, and the form needs no backend code. |
| 2026-11-01 | Thin buckets show fewer items; never pad with another mood's items. Rejected: padding. | Incoherent results break the core promise. Fewer results is honest and shows which bucket needs curation. |
| 2026-11-01 | The results page shows the detected mood (e.g. "Sounds nostalgic"). | Near-zero cost, makes the classification visible, helps on a portfolio piece. |
| 2026-11-01 | Each song links out to an external service; the URL is stored in the dataset item. Link format is a TDD detail (see Q9). | Gives the visitor somewhere to go from a result. |
| 2026-11-01 | Books and pictures stay out of V1 (books V2, pictures V3). The dataset schema has a `type` field (`song` or `quote`). Rejected: adding books to V1. | Books add about a week of curation to a ~20-hour budget; pictures add licensing, hosting and subjectivity problems. Both are on the Project Plan's skip list. |
| 2026-11-01 | The taxonomy includes a "lost" bucket for uncertain or unsettled feelings. The classifier may also return `unclear`, which is not a bucket and has no items; the handler turns it into a friendly message. Rejected: no "lost" bucket. | Uncertain feelings are legitimate input and deserve results; input with no mood needs a clean no-result path. (Resolves Q7: how should the taxonomy and classifier handle uncertain feelings versus input with no mood?) |
| 2026-11-01 | Prompt-injection handling: the prompt tells the model to return `unclear` for instruction-style input, and the code guarantees only enum-or-`unclear` output. The eval's injection set (5-8 phrases) must pass 100%. A valid bucket returned for an injection phrase is a fail. The README must not claim injection-proof. | Injection can't be detected deterministically. Damage is bounded (no tools, no data), and a strict pass condition is the achievable V1 guarantee. |
| 2026-11-01 | Classifier eval: 90% on typical phrases (~20 in the first set). `acceptable` moods are written generously and before running. Ambiguous and injection phrases are reported separately. It is a sanity check for gross errors and a regression check after prompt changes, run on demand against the real classifier. Rejected: 80% (too loose), 98% (needs a far larger sample, invites overfitting). | One phrase is worth 5 points; 90% leaves room for labeler disagreement and LLM variance. Near-synonym distinctions are a V2 taxonomy matter. |
| 2026-11-01 | Within a mood, results are a random sample with an injected random source (seeded in tests). Rejected: fixed order, deterministic shuffle. | Repeat visitors see variety, tests stay exact, and a deterministic shuffle solves a problem that disappears in V2. |
| 2026-11-01 | CI runs `go vet` and unit tests on every change using a fake classifier and fake LLM client; `-race` is added in Week 5. The eval is not in CI. Production failures are caught via logs, `/healthz` and the provider dashboard. Rejected: running the eval in CI. | Each layer guards a different failure point: CI catches code bugs, the eval catches prompt regressions, logs and healthchecks cover what's live. |
| 2026-11-01 | Keep project docs in the repo under `docs/`, with a `docs/v<N>/` folder for each milestone. Rejected: keeping docs only in the Claude Project. | Docs sit next to the code and change in the same PR, so the reason for a change stays attached to it. |
| 2026-11-01 | Name the shared docs `project_plan.md`, `open_questions.md` and `decision_logs.md`. Rejected: `decisions.md` and `open-questions.md`, the earlier example names. | Matches the layout specified for the repo. |
| 2026-11-01 | A resolved open question is removed from `open_questions.md` and logged in the Decision Log as a row ending "(Resolves Q#.)". Question IDs are never reused. Rejected: keeping a Resolved table in `open_questions.md`. | The open questions file then holds only what is still open, and the Decision Log is the one place to look for why something was decided. |
| 2026-11-01 | Non-project to-dos live in `docs/todo.md`, each with a trigger for when to do it. No TODO or FIXME comments in code. Rejected: inline TODO comments. | Follow-ups stay visible in one place and don't pile up as comments across the codebase. |
| 2026-11-01 | Project skills live in `.claude/skills/` and are committed to the repo. They are run by the user only (`disable-model-invocation`), starting with `/create-pr`. Rejected: letting Claude invoke them on its own; keeping skills in the user's global config. | Pushing a branch and opening a PR are outward-facing, so they should only happen on request. Committed skills give the same workflow on every machine and show up in review. |
| 2026-11-01 | Each version ends with a retro in `docs/v<N>/retro.md`. The PR template asks for decisions, open questions and to-dos as "logged, or none", because not every PR has one. Rejected: a checklist that requires a decision in every PR. | The retro hands over what the next version needs from this one. The "or none" wording keeps the template honest. |
| 2026-11-01 | `CLAUDE.md` imports only the decision log and the current version's weekly plan and TDD, and lists other docs by path. Rejected: importing every doc in every session. | Keeps per-session context small while always loading what constrains current work. |
| 2026-11-01 | Every change starts on a new branch and goes through a PR; nothing is committed or pushed to `main` directly. Rejected: committing small docs changes straight to `main`. | Each change stays reviewable and revertable on its own, and the PR is where the docs hygiene check runs. |
| 2026-11-02 | V1 allows 6-9 moods (was 6-8) to fit `energetic`, a distinct high-energy mood (new project, resolution, gym goal). The V1 list is capped at 9: other ideas (hopeful, melancholy, demotivated, aloof) are parked as Q11 for V2. Rejected: swapping out `anxious` or `calm`; keeping the cap at 8. | `energetic` has no close neighbour among the other eight, so it should not hurt the 90% eval. It adds about 6-10 items, which stays inside the 50-100 range. Near-synonym moods remain a V2 matter. |
| 2026-11-02 | V1 allows 6-10 moods (was 6-9), adding `heartbreak` as its own bucket next to `love`; 10 is the final V1 count. Heartbreak is a very common mood for the target user and needs its own songs and quotes. Rejected: folding heartbreak into `love` or `sad`; an LLM-returned tone score within a bucket; adding `spiritual` (parked in Q11). Supersedes the cap of 9 in the earlier 2026-11-02 row. | A separate bucket is the V1 way to get finer results: a score adds a second dimension that is unreliable to produce, can't be checked by the eval, and doubles curation. Graded closeness belongs to V2 (see Q12). A mixed `love` bucket could show a giddy song to a heartbroken user. 10 moods at 5-10 items still fits the 50-100 range. |
| 2026-11-02 | The V1 taxonomy is frozen at ten moods: happy, sad, angry, calm, anxious, nostalgic, lost, love, heartbreak, energetic. It lives in one embedded taxonomy file with a `key`, `label` and `definition` per mood; code holds no mood literals, the loader validates dataset tags against it at startup, and tests and the eval hardcode the keys on purpose. Love is romantic only. Rejected: mood names hardcoded in each place; numeric ids; a single `love` bucket covering heartbreak; an LLM-returned tone score. (Resolves Q1, Q8.) | A mood name appears in about seven places, so one source of truth plus a startup check turns a silent data loss into a boot failure. Hardcoded test keys keep the tests an independent check. Definitions feed the classifier prompt, so they were written to be testable against a phrase. |
| 2026-11-02 | Song items carry `title`, `artist` and `urls`, a map keyed by service with only `spotify` and `youtube` allowed. URLs are direct track links; at least one is required. The loader checks keys, `https` and the host per service at startup. Links are checked by hand before launch. Link-out only. Rejected: search URLs; a single `url` field; a list of URLs; requiring both services. (Resolves Q9.) | Direct links give the best experience, and two services give a fallback when one link rots. A fixed key set and host check turn typos and misplaced URLs into boot failures, as with the mood taxonomy. `title` and `artist` leave room for a music API later (Q13), and the map makes a per-service filter possible (Q14). |
| 2026-11-02 | Optional extras live in `docs/nice_to_have_features.md`, an inventory checked at each milestone wrap-up. `open_questions.md` keeps only unresolved design questions. Rejected: parking every later-version idea as an open question. | Extras are not questions waiting for an answer, and mixing them in makes the open questions file harder to scan. A separate inventory is quicker to read and review. |
| 2026-11-02 | `/recap-learning` is a project skill that outputs a copy-pastable recap of the session's questions, the user's quoted answers, corrections and learning, and writes nothing to disk. The learning record itself stays local and excluded from git. Rejected: having the skill write into the learnings folder; committing the learning notes. | The notes are private and in the user's own words, so the skill only produces text and the user pastes it. Keeping it output-only means it can never stage or leak the private folder. The skill itself is committed because it shows how learning was prioritised, and it reveals none of the content. |
| 2026-11-04 | TDD drafting progress is tracked in `docs/v1/tdd_outline.md`: every section, what is known, what is still to decide, and a status. The file is deleted when the TDD is final. Rejected: adding status columns to `tdd.md` itself. | The TDD stays a clean spec that a developer can read, while the checklist can change freely as topics close. It is listed by path in CLAUDE.md, not imported, to keep session context small. |
| 2026-11-04 | The V1 classifier starts on Google Gemini with a Flash-Lite model, with OpenAI as the planned fallback; the exact model IDs are config values confirmed in Week 3 and by the eval. Provider-specific code lives in one package, and provider and model name come from config, so a pivot is cheap. Rejected: Anthropic Haiku 5.5 as the start; OpenAI first; a fine-tuned open model such as `j-hartmann/emotion-english-distilroberta-base`; a larger model from the start. | All candidates cost a fraction of a cent per request, so cost does not decide. Flash-Lite is the cheapest tier that may be accurate enough, and the eval tells us if it is not. Keeping SDK calls behind one boundary turns a provider switch from a refactor into about 3-5 hours of adapter and prompt work. The open model has 7 fixed labels that do not match the taxonomy and no `unclear` class. |
| 2026-11-04 | The V1 hosting target is deferred to the start of Week 6 (Q15). Until then the service meets host-neutral portability requirements: one container image, config and secrets from env vars, platform-provided port, graceful shutdown, `/healthz`, a single instance. Rejected: choosing a host now; deploying early to a throwaway host. | Build and test come first and nothing in them depends on the host. The portability requirements make the Week 6 choice cheap, and the research (spin-down against the 3 s criterion, in-memory counters, price) can finish in the meantime. This moves the hosting decision out of Week 2 (see the weekly plan change). |
| 2026-11-04 | V1 uses Go 1.27 (latest stable) with the standard library first: `net/http` `ServeMux` for routing, `testing` and `httptest` for tests, `html/template`, `slog`; CI static checks are `go vet` and a `gofmt` check; dependencies are limited to the LLM SDK. Rejected: a router or web framework (chi, gin, echo); an assertion library such as testify; a lint suite such as golangci-lint in V1; an older Go release. | Three routes do not need a router library, and the standard library is part of what is being learned. Fewer dependencies mean less to audit and upgrade. chi is `http.Handler`-compatible, so adding it later is cheap. A lint suite adds configuration for little gain at this code size. |
| 2026-11-04 | Moodwise is one Go module and one deployable, a modular monolith: later categories and sources are packages behind interfaces, not separate services. Go stays for V1 to V4; Python is revisited only if the project needs local models or a Python-only library, and then as one small service behind an interface. Rejected: microservices; Python for the main service; a separate repo for the frontend. | Microservices would add distributed-systems problems before V3's concurrency work needs them. Go was chosen to match the work backend, and it suits V3 (goroutines, `context`, `errgroup`) and V4. V2's embeddings need only an embeddings API call and cosine similarity over a few hundred vectors, which is a few lines of Go, so Python's stronger ML ecosystem does not pay for a second language. |
| 2026-11-04 | The frontend is server-rendered: Go `html/template` pages with htmx for interactivity (loading state and result swaps; streamed results over Server-Sent Events in V3) and small vanilla JS where needed. Templates and static assets are embedded with `go:embed`. htmx is vendored at a pinned version in `web/static/`, never loaded from a CDN. A JSON API (`POST /api/match`) stays alongside the pages, and match logic returns data that both handlers only render. A separate single-page app is a V4 revisit (Q16). Rejected: a single-page app from V1; a separate frontend project; htmx from a CDN. | V1's UI is one form and one results page. A SPA would add a Node toolchain, a second build and more generated code to review, competing with the backend learning that is the goal. Server rendering escapes output by default, keeps one language and one deployable, and fits SSE streaming. The JSON API lets a SPA or a mobile client reuse the backend later, so this is not a one-way door. Vendoring htmx avoids a third-party request on every page load. htmx is a static file, not a Go module dependency. |
| 2026-11-04 | V1 includes one timeboxed design pass (about 1.5 hours, Week 4): design tokens as CSS variables in one file, reused by every page; what goes in them is decided in the TDD's "Frontend and design system" section. Week 1's throwaway page uses a minimal version of the tokens. If Week 4 runs long, polish items are cut first. The project plan's "deployed live, even if ugly" is relaxed to a clean, modern look. Rejected: styling page by page during feature work; an unbounded polish phase; leaving the look to V4. | A UI the author is proud of keeps a part-time solo project going. Tokens in one place make a restyle one edit, and V3's new categories reuse the same components and stay consistent. The timebox keeps design from taking backend hours. |
| 2026-11-04 | The "standard library first" and "dependencies limited to the LLM SDK" rules of the 2026-11-04 Go row are V1-scoped and refer to Go module dependencies. Later versions add libraries when they need them, each with its own decision row at the start of that version; the likely picks are in `docs/todo.md`. Rejected: carrying the V1 dependency list into V2 to V4 as a rule; choosing the V3 and V4 libraries now. | V3 needs a Postgres driver and a metrics library, and V4 needs auth and rate limiting. Choosing them now is guessing; choosing them at the start of each version keeps the decision next to the need. Fixing the seams now (interfaces, packages, the JSON API) is what keeps those later additions cheap. |
| 2026-11-04 | The server depends on a single `Matcher` interface (phrase in, outcome out), not on `Classifier` and `Catalog` directly. V1's matcher classifies the phrase, then looks up the mood bucket. Rejected: the handler calling the classifier, then the catalog, then rendering. | "Classify, then look up the bucket" is a V1 detail. V2 matches by embeddings with no mood in the middle, so a handler that orchestrates those steps would be rewritten in V2. Behind a `Matcher`, V2 adds a second implementation and the handler is untouched. |
| 2026-11-04 | `Classifier` is an interface, implemented by the LLM classifier and a test fake, with everything provider-specific in the provider adapter behind it. Rejected: a concrete classifier type called directly by the matcher or handler. (Resolves Q2.) | Tests can make the fake return a mood, `unclear`, a timeout or an off-list answer on demand, with no network, cost or flakiness. A provider switch changes one adapter, not the matcher or the handler. |
| 2026-11-04 | The taxonomy is read and validated once at startup into an immutable value that the classifier, the dataset loader and the templates receive; none reads the file itself. Rejected: each consumer reading the file. | One read means one validation and one place to fail at boot, and the consumers cannot disagree about the moods. Tests pass in a small taxonomy instead of writing files. |
| 2026-11-04 | `Catalog` is an interface (retrieval by mood key, random sample with an injected random source), defined where the matcher uses it. Rejected: the matcher using a concrete catalog type. | Matcher tests can fake a thin or empty bucket without a loaded dataset, and in V2 the catalog moves behind a `Source` interface without touching the matcher. |
| 2026-11-04 | The server maps the matcher's outcome to a view model that templates render, and templates are parsed once at startup. Rejected: passing domain types to templates; parsing on each request. | Templates stay display-only, which keeps "handlers render, they do not decide" enforceable. A template syntax error stops boot instead of causing a 500 on the first request. |
| 2026-11-04 | Request ID, access logging, panic recovery, the spend guard, security headers and timeouts are middleware, applied in a fixed order, not code inside handlers. Rejected: each handler doing its own. | A new route inherits every concern automatically, and the forgotten-concern bug cannot happen. |
| 2026-11-04 | Config is read from environment variables and validated once at startup, and one composition root (`cmd/moodwise`) creates and wires every concrete component. Nothing else reads the environment. Rejected: components reading environment variables or building their own dependencies. | Missing values fail at boot, tests construct config and components directly with fakes, and there is one place where the wiring is visible. |
| 2026-11-08 | `unclear` and a thin or empty bucket are outcomes with a friendly message; timeout, provider error and invalid output are typed errors. The LLM is called once per request with a generous, configurable timeout (starting guess 6 s, set after Week 3 measurements) derived from the request context, with no automatic retry, and a failed request offers a "Try again" button. The PRD's 3 s criterion stays as a typical-case target. Rejected: an automatic retry with the PRD loosened to about 10 s; treating `unclear` as an error. | A timeout usually means a slow or down provider, so a retry would likely fail again, double the wait and possibly be billed twice. Retries and a circuit breaker are V3 work. A manual retry gives the visitor control and passes through the spend guard like any request. The context deadline stops paying for answers nobody will see. |
| 2026-11-08 | The spend guard is not middleware: it runs after input validation, just before the paid LLM call, so rejected input never counts against the budget. The mechanism and whether it wraps the `Matcher` or the `Classifier` are settled with Q5. Rejected: the guard in the middleware chain before the handler. Amends the middleware order in the 2026-11-04 row on request ID, logging, recovery and the spend guard; that row stays. | Middleware cannot see whether input is valid, so a flood of empty submissions would use up the daily budget on requests that cost nothing. The guard protects the paid call, so it belongs next to it. |
| 2026-11-08 | The browser form posts to `POST /match` and gets HTML (a fragment for htmx requests, a full page otherwise); other programs use `POST /api/match` and get JSON. Both call the `Matcher` directly and differ only in rendering. The phrase is always sent in a POST body, never in a URL. Rejected: one JSON route with browser JavaScript rendering it; the page route calling the JSON API over HTTP; a GET form. | The page works without JavaScript and stays server-rendered. Calling our own API over HTTP adds a hop and runs middleware twice. A GET would put phrases in history, proxy logs and the `Referer` header, so logs would need hand-stripping. |
| 2026-11-08 | Both routes return the same real HTTP status codes from one shared mapping, and errors reach the page as an error view model of kind, message and a Try again flag; provider detail goes only to the log, written once by the handler. htmx is configured to swap 4xx and 5xx responses, with a test. Rejected: the page route returning 200 with an error fragment. | A 200 for a failure would make the access log and any platform monitor that charts 5xx show failures as successes, and give the page route its own status rule. The cost is one htmx setting, and an unconfigured htmx would drop error responses and leave a blank page, which the PRD forbids. |
| 2026-11-08 | `/explain-topic` is a project skill that explains any topic the user names (a TDD section, code, a concept, background context) in simple words. It always uses one easy example that runs through the answer, opens with the whole flow or story, then gives each point with its place in that flow. It outputs text only and is run by the user only. Rejected: limiting it to TDD drafting; making the example optional; leaving explanations to ad-hoc prompting each time; a skill that edits docs while explaining. | The user could not connect a list of design points to the overall flow, and the fix that worked was a simple example, the flow first, then each point with its context. The need is wider than the TDD, since the user also wants to get familiar with code and context. A skill makes it repeatable, and keeping it read-only means an explanation can never change the spec by accident. |
| 2026-11-08 | `taxonomy.json` and `items.json` live in `content/` and are embedded in the binary with `go:embed`; config has no dataset path. Rejected: reading the file from a path set by an environment variable; `items.json` at the repo root; fetching content at startup. | `go:embed` can only reach files in its own folder or below, and the repo structure plan already keeps curated content in `content/`, separate from code. Embedding ships one artifact whose content and code versions always match, and removes a config value that could be wrong. A content edit needs a redeploy, which is fine for one editor. |
| 2026-11-08 | Items have an explicit stable `id` (`s-` or `q-` plus a number, never reused), exactly one `mood`, and no duplicates anywhere in the file (id, song link, title and artist, quote text and author). Quotes need `text` and `author`, with an optional `source`; no lyrics, and a quote with an unknown or disputed author is left out. Quote authors are checked by hand before launch. Rejected: position or title-derived ids; several moods per item or one track under two moods; optional authors; lyrics as quotes. | A song under two moods can come back for two different feelings and looks like a bug to the visitor, and it doubles the hand review. V2 attaches precomputed data to items by id, so ids must survive reordering and edits. Misattributed quotes and lyrics undermine the honest dataset and raise copyright questions. |
| 2026-11-08 | The loader decodes into private file-shape structs and rejects unknown fields, then builds the domain types. It collects every error with item ids and stops boot. A thin or empty mood is a startup warning, not an error. A CI test loads the real `content/` files, and from Week 5 a stricter test, kept in CI, requires every mood to fill 3 songs and 2 quotes. Rejected: stopping at the first error; skipping bad items; failing boot on a thin bucket; using the file shape as the domain type. | Collecting errors makes curating 50+ items practical, and skipping an item would lose it silently. Failing boot on thin buckets would block Weeks 1 to 3, so the strict check moves to a CI test from Week 5, which then also stops a later edit from emptying a bucket. Separate shapes keep a file-format change out of handlers and templates. |
| 2026-11-08 | The catalog is an index built once at startup and never changed. Sampling picks distinct positions and never reorders the shared lists. Randomness is an injected function (a number below n): production passes the top-level `rand.IntN` from `math/rand/v2`, tests pass a scripted one. The matcher owns the 3 songs and 2 quotes as named constants, not config. Rejected: shuffling the shared slice; one shared `*rand.Rand`; a global source; a lock around the index. | Concurrent requests shuffling a shared slice is a data race that appears only under load. A shared `*rand.Rand` is not safe for concurrent use. A scripted function lets tests assert exact picks and the edges (bucket smaller than the request, no repeats, empty bucket). Matches the earlier decision that the catalog takes an injected random source. |
| 2026-11-08 | A thin bucket, or one with no songs or no quotes, is a normal result: the empty section is hidden, and if both are empty the page shows the mood with a friendly "no picks yet" message, the handler logs a warning, and the status is 200. A mood key outside the taxonomy is a typed catalog error that becomes the unexpected-failure 500. Rejected: padding; treating an empty bucket as an error; treating an unknown key as an empty bucket. | An empty bucket is a curation gap, not a fault, and padding would break the promise that results match the mood. An unknown key means a wiring bug, since the classifier already validates its answer, and a friendly empty page would hide it. |
